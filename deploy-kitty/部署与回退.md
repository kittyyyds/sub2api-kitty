# Kitty Canvas 部署与回退

日期：2026-09-21。本文对应当前候选 SUB `.5` 与独立 Canvas Next 服务。原 `.4` 包和原线上部署不在本目录的修改范围。本文记录静态核对和待执行步骤；本次未执行 Docker 构建、容器启动、Nginx 配置装载或生产切换。

## 服务与路径

Canvas 是独立 Next 服务，浏览器与 SUB 主站同源。它读取主站登录身份，使用 Key ID 委托到 SUB，且项目、素材、生成历史保存在浏览器按账号隔离的 IndexedDB。容器不挂媒体、工程或账户数据卷。

| 浏览器路径 | 目标 | 说明 |
| --- | --- | --- |
| `/canvas` | 跳转 `/canvas/canvas` | 画布工程列表入口 |
| `/canvas/…` | 宿主机 `127.0.0.1:3101` | Next 的编译时 `basePath=/canvas`，保留完整 URI |
| `/api/v1/canvas/…` | 原 SUB 上游 | bootstrap、模型与报价，保持原 `/api/v1` 反代 |
| `/canvas-api/v1/…` | 原 SUB 上游 | 已登录用户的 Key ID 委托、生成、状态与下载 |
| `/v1/…` | 原入口线路 | 原配置原样保留 |
| `/canvas/source/kitty-canvas-source.tar.gz` | 只读源码归档 | 必须对应本次实际发布的修改版源码 |
| `/canvas/source/LICENSE` | 只读许可证文件 | 与 `canvas/LICENSE` 保持逐字节一致 |

`SUB_EXISTING_UPSTREAM` 表示现场现有 SUB 反代的 upstream 名称或 `host:port`。SUB 应用常用内部端口为 7070，但内部端口、容器映射端口和 Nginx upstream 是不同概念；使用现有配置中的实际值。本文不给线上端口赋默认值。该片段面向宿主机 Nginx；Nginx 若运行在另一个容器，其 `127.0.0.1` 不代表宿主机，应先解决既有网络拓扑后再采用片段。

## 镜像与文件布局

使用仓库根目录的 `Dockerfile.kitty`，构建上下文必须是本 Canvas 仓库根目录。`deploy-kitty/compose.canvas.yml` 的 `context: ..` 从本目录指向仓库根目录。不要改为 `web/`：Dockerfile 还需要根目录 `VERSION` 和 `CHANGELOG.md`。下文命令均以本目录 `deploy-kitty/` 为工作目录。

Dockerfile 的构建阶段在 `/app/web` 执行 `npm ci` 和 `npm run build`，构建时设置 `NEXT_PUBLIC_KITTY_MODE=true`。运行阶段把 `/app/web/.next/standalone` 的内容复制到运行目录 `/app/web`，入口为 `node server.js`；`web/.next/static` 和 `web/public` 分别复制到 `.next/static`、`public`。该镜像仅包含 Canvas Next 运行服务，不启动原 Canvas Go 账户服务。

`NEXT_PUBLIC_KITTY_MODE` 影响编译结果，运行时补环境变量不能把普通 Canvas 镜像转换为 Kitty 版。Compose 以 UID/GID 1000 运行，宿主机仅发布 `127.0.0.1:3101`，运行限制为 1 CPU、1 GiB 内存、256 个进程。构建进程不受这些运行时限制约束，应在独立构建环境完成。生产记录实际镜像 digest，避免用可变的 `latest` 作为回退依据。

根文件系统设置 `read_only: true`。`/tmp` 使用 64 MiB tmpfs，`/app/web/.next/cache` 使用 128 MiB tmpfs，并赋予 UID/GID 1000 写权限；tmpfs 计入容器内存额度，重建容器会清空缓存。源码中目前未发现 `revalidate`、`generateStaticParams` 或自定义运行时文件写入，但这不是容器运行证明。候选环境必须检查首页、工程列表、静态资源及日志，确认没有 `EROFS`/`EACCES` 后再投放；若将来添加 ISR 或其他写入路径，应定位并追加最小临时目录，不应取消整个只读根设置。用户项目不依赖这些缓存。

## 分阶段执行

### 1. 固定候选材料与旧版回退材料

保留原 `.4` 镜像的精确 digest、原 SUB 启动配置和原 Nginx 配置备份。候选 `.5` 镜像及源码使用独立标签，不覆盖 `.4`。保留本目录的 `LICENSE.canvas` 以及 Canvas 根目录 `LICENSE`；最终打包结束后生成修改版完整对应源码 `kitty-canvas-source.tar.gz`，包含源码、`Dockerfile.kitty`、锁文件、`VERSION`、`CHANGELOG.md`、许可证和本次部署材料。排除 `.git`、`node_modules`、`.next`、缓存、运行数据、私有环境文件和任何登录材料。下载归档不得用上游未修改源码代替。

将最终源码归档与逐字节复制的 `LICENSE` 放到 `CANVAS_SOURCE_DIR` 指定的只读发布目录，并校验 SHA-256。Nginx 只开放两个精确文件地址，不开启目录列表。源码下载与许可证应在 Canvas 对外开放前可用，前端菜单保留对应链接。

源码归档应在所有实现与部署材料提交后，直接从实际发布提交生成。以下命令从仓库根目录执行；`git archive HEAD` 只包含已提交文件，生成的公开文件由精准 `.gitignore` 规则排除，避免归档自包含。`HEAD` 必须就是待构建版本，不能有尚未提交的源码或部署修改。归档包含根 `LICENSE`、原项目说明与归属、`VERSION`、`CHANGELOG.md`、`Dockerfile.kitty`、前端源代码与锁文件、原有公共资源及 `deploy-kitty/`。

```sh
mkdir -p web/public/source
git archive --format=tar.gz --prefix=kitty-canvas/ --output=web/public/source/kitty-canvas-source.tar.gz HEAD
cp LICENSE web/public/source/LICENSE
(cd web/public/source && sha256sum kitty-canvas-source.tar.gz LICENSE > SHA256SUMS)
```

禁止把工作目录整体直接压缩：归档应排除 `.git/`、依赖安装目录、`.next/`、其他构建缓存、运行数据库和媒体、私有环境文件、登录材料以及生成归档本身。允许保留公开 `.env.example`。现有 `.dockerignore` 不排除 `web/public/source/`，因此 Docker 构建会携带已生成的公开源码与许可证；生成归档必须先于 Docker build。生产模板仍使用两个精确 Nginx 静态地址，可将 `CANVAS_SOURCE_DIR` 指向该目录或其只读发布副本。不要把整个发布工作区映射成公共目录。

旧自动部署任务不得部署 `.5`。投放前先核对其目标标签/文件名和调度内容，仍指向原已批准版本，或保持停用；本任务不重用、不改写旧低峰自动计划来安排 `.5`。Compose 的 Watchtower 排除标签仅是辅助设置，不能代替该检查。

### 2. 先启动独立 Canvas，与 `.4` 共存

以下命令是待执行示例，工作目录为本仓库的 `deploy-kitty/`。先给 `CANVAS_IMAGE` 赋予审核后的明确镜像标签；远端镜像可使用 digest。这里只操作名为 `kitty-canvas` 的 Compose 项目。

```sh
export CANVAS_IMAGE='REVIEWED_CANVAS_IMAGE_TAG_OR_DIGEST'
docker compose -f compose.canvas.yml config --quiet
docker compose -f compose.canvas.yml build canvas
docker compose -f compose.canvas.yml up -d --no-build canvas
docker compose -f compose.canvas.yml ps
curl --fail --silent --show-error --output /dev/null http://127.0.0.1:3101/canvas/canvas
docker compose -f compose.canvas.yml logs --tail=100 canvas
```

已由可信构建环境提供镜像时，以 `docker compose -f compose.canvas.yml pull canvas` 替代本机 build；不要对 digest 引用执行本机构建。健康检查仅发出 GET `/canvas/canvas`，不请求报价、模型生成、计费或下载接口。这一步只确认 Next 页面存活，不证明 `.4` 已提供 Canvas 后端接口。

此阶段不装载新的 Nginx 片段、不加主站画布入口、不切 SUB 镜像。原 `.4` 可继续服务；Canvas 仅在宿主机 loopback 可达，其客户端初始化尚不能依靠 `.4` 完成。不要将健康状态写成“画布已完整接入”。

在候选主机额外核对 `docker inspect` 中的 `ReadonlyRootfs`、端口绑定、内存/CPU 限制和两个 tmpfs；检查页面及静态资源访问后没有只读目录错误。本次只准备这些检查步骤，尚未运行它们。

### 3. 单独安排 `.5` 切换与入口开放

`.5` 切换是独立于既有低峰计划的发布动作。先检查其他代理提交的后端测试、前端构建与本地验收证据，再使用新发布窗口执行；不要让旧自动任务拾取 `.5`。切换时暂停新视频提交，按原 SUB 优雅停机步骤排空在途请求，再用候选 `.5` 精确镜像替换原 SUB 服务，沿用原数据库、Redis 和全部原有运行参数。

读取当前 Nginx upstream 并设置模板变量。渲染时只替换下列两个变量，保留 Nginx 自身的 `$host`、`$remote_addr` 等变量：

```sh
export SUB_EXISTING_UPSTREAM='EXISTING_SUB_UPSTREAM_NAME_OR_HOST_PORT'
export CANVAS_SOURCE_DIR='/ABSOLUTE/REVIEWED/RELEASE/SOURCE_DIRECTORY'
envsubst '${SUB_EXISTING_UPSTREAM} ${CANVAS_SOURCE_DIR}' < nginx.canvas.locations.conf.template > nginx.canvas.locations.conf
```

把渲染片段纳入既有同源 HTTPS `server`。保持既有 `/v1`、`/api/v1`、证书、真实客户端 IP 信任、访问控制和上传大小设置。新 `/canvas-api/` 位置应继承同一站点既有访问策略；如果原配置已有同等路由则保留原块，避免重复 location。随后先执行 `nginx -t`，成功后按站点既有流程 reload。

在同源浏览器检查主站登录跳转、bootstrap、Key/模型目录、只读视频任务列表、账号切换后本地工程隔离、静态资源和源码下载。余额查询和只读页面不代替生成验收。任何生成验收应使用单独明确的测试安排，不加入存活检查、定时健康任务或该部署脚本。

确认 `.5` 与 Canvas 都就绪后才开放主站入口。入口与 `.5` 同时可见时，切换窗口中应先保证 Next 已在 loopback 健康、反代已通过语法验证，再对外完成切换，避免留下指向未启动服务的入口。

## 回退

1. 停止开放新画布生成，保留当前候选日志、镜像 digest 和数据库备份；已有视频任务 ID、dedup 与 usage 记录保留。先恢复主站原入口状态并移除本次 Nginx 的 `/canvas`、`/canvas/`、源码和 `/canvas-api/` 新增块（已有等价 SUB 路由恢复到备份），`nginx -t` 成功后 reload。
2. 按现有 SUB 发布流程优雅停止候选 `.5`，恢复记录下来的原 `.4` 镜像 digest和原运行配置，沿用原数据库与 Redis。不要运行旧自动任务去猜测“上一版”。保持原 `/v1` 入口和线路，随后只做既有无计费健康检查与只读页面检查。
3. 本次未新增数据库迁移；回退无需删表、改列或还原数据库到旧快照。`.5` 已写入的 `usage_billing_dedup`/archive、`usage_logs` 和 `video_tasks` 使用既有表结构，必须一并保留。尤其不能删除 dedup 或将已扣费任务改回未结算来“清理”候选数据，否则可能重复扣款。`.4` 不具备 `.5` 新增的完整票据修复保障，候选期间处于 `pending`、`unknown` 或 `needs_review` 的任务应逐条核对后再安排后续处理。
4. 待 SUB 恢复稳定后，可执行 `docker compose -f compose.canvas.yml stop canvas` 停止独立 Canvas。用户浏览器 IndexedDB 不会被该命令删除；用户可通过同一来源和账号再次打开兼容 Canvas 后恢复本地工程。服务器没有 Canvas 媒体数据卷可迁移或删除。

不要使用 `docker compose down -v`、删库或清理结算记录作为回退步骤。回退完成的证据应包括：原镜像 digest、原 `/v1` 路由未改、原面板可读、候选路由已撤、没有新迁移回滚，以及在途视频任务的核对状态。
