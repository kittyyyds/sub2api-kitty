## 发布、备份和连接处理

备份位于 `/opt/kitty-recovery-20261008/monitor-path/<site>/`：在线数据库dump、原二进制、受限容器配置、原路由及执行回执；本机资料在 `D:/AI-Storage/Reviews/kitty-monitor-path-20261008`。没有上传客户数据库或凭据到GitHub。

kittyapi首个候选启动时发现受管模式禁止自动迁移，准备检查失败，未切生产路由。将缺失的新增迁移单独在事务中执行、记录与构建内容一致的SHA256；使用迁移咨询锁、750ms锁超时和5秒查询超时。停止失败候选后重新启动并完成全部预热验收。kittyyyds发布已提前包含该步骤。

kittyapi约21:00:11、kittyyyds约21:04:32接管新请求；Caddy热加载/接力路由切换，保留旧请求排空。21:06验收kittyapi旧实例已安全排空停止；kittyyyds旧实例仍有6条WebSocket连接，保持draining且后台任务已交接，未强制断开。不能据此保证每一个客户请求都绝对无感。

回滚使用保留的上一版二进制创建新受管实例，保持新增兼容列，不恢复旧数据库、不回滚新产生账务。kittyapi回退时只替换本站目标，保留其他路由。若要连同GLM配置回退，原配置为provider=openai/request_path空；旧版本不识别新路径时不可保留zhipu分类，否则会恢复原404。
